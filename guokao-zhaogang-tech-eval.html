2.1.1 题库系统

子功能 技术实现 难度

技术栈：后端题目服务 + 关系型存储（题目表/答题记录表）+ Redis（答题会话）

技术点 1题库系统基础（管理/组卷/客观判题/错题）

- 处理的问题：题目管理、组卷、客观题判题、错题记录与复习。
- 怎么做的：题目结构化表 + 标签体系（科目/题型/难度/知识点）→ 组卷规则（知识点权重+难度配比+滑动窗口防重复）→ 客观题选项比对判题（确定性逻辑）→ 错题本 + SRS 间隔重复（SM-2/FSRS 成熟算法）→ 主观题只做"参考点评"不判分。
- 可能遇到的问题：
1. 系统本身零风险，风险全在"内容从哪来"（题目素材获取见技术点 2）
2. OCR 对图表题数字抽取准确率低 → 图表题走人工录入或标注"仅文字题"
- 结论：系统层可行（判题 100% 一致、组卷偏差≤5% 可验证）；内容层见技术点 2，两者必须分开评估。

技术点 2历年真题库的快速积累

- 处理的问题：10 万+ 道行测/申论/面试真题 + 答案解析。
- 怎么做的：爬取公开题源 → OCR + 人工校对 → 知识点打标 → 解析编写 → 入库。
- 可能遇到的问题：
1. 版权关（粉笔/中公/华图题库为商业资产，公开可合法获取的完整真题源极少）
2. 人力成本关（每道题 5~15 分钟 → 10 万题 ≈ 4~12 人年）
3. 答案解析本质是"知识生产"而非"数据处理"，自动化上限低
- 结论：不是技术问题，是版权+人力成本问题；缓解路径只有采购/合作/众包/分步积累，自建 10 万题会严重超期超支。

技术点 3主观题（申论/面试）AI 权威评分

- 处理的问题：对申论大作文、面试回答给出"可信的分数"。
- 怎么做的：LLM 结合评分维度生成评分 → 展示分数 + 点评。
- 可能遇到的问题：
1. 缺权威 ground truth（官方评分标准不公开，无法建立训练与评测基准）
2. 相关性上限（LLM 与人工评分约 0.6~0.8，不足以承担"权威评分"）
3. 责任关（错误评分直接影响考生判断，无法兜底）
- 结论："权威评分"当前不能实现；可降级为"AI 参考点评"（结构化的优点/不足/建议，明确非评分）——立项时应主动放弃"AI 判分"卖点。

技术点 1职位表结构化入库

- 处理的问题：把官方发布的《招考简章.zip》（Excel 职位表，2026 年 20,714 岗位 / 38,119 人）转成结构化数据库。
- 怎么做的：官方专题站"相关下载"获取 Excel → openpyxl/pandas 解析 → 字段映射标准化（枚举字段编码化、空值统一）→ year 分区表 + 年度导入脚本 + 对账任务。
- 可能遇到的问题：
1. 每年表头/格式可能微调 → 字段映射必须配置化，不能硬编码列名
2. 专业字段存在三种粒度（大类/枚举多个具体专业/门类/"不限"），解析时必须保留粒度信息（技术点 2 的地基）
- 结论：技术风险低，工作量集中在"每年对账 + 字段漂移兜底"，可验证（岗位数=官方数、抽样字段一致率≥99.5%）。

技术点 2专业三级目录匹配

- 处理的问题：判断"考生专业"是否命中"岗位专业要求"。三级目录（门类 2 位 → 大类 4 位 → 具体专业 6 位），且税务系统用独立目录，本/硕/专三套目录并存。
- 怎么做的：官方目录（含税务目录）建树形表 + 年度版本 → 三路并联匹配（6 位精确 / 4 位前缀 / 2 位前缀，+"不限"恒命中）→ 交叉学科映射表（考生专业→可报大类集合，人工维护约数百条）→ 税务目录独立分支。
- 可能遇到的问题：
1. 岗位专业要求一行内可能混合多种写法（"计算机类、电子信息类"），必须拆集合再匹配
2. 每年目录新增专业 → 需"目录版本化 + 年度 diff"
3. 目录外专业的覆盖靠映射表运营补齐，召回率预期内达不到 100%
- 结论：规则可达 99% 精确率（2-3 周），剩余风险是"目录外专业"覆盖，靠映射表运营解决，不构成技术阻塞。

技术点 3硬性条件筛选（规则引擎）

- 处理的问题：按学历、学位、政治面貌、是否应届、基层服务项目、基层工作年限、性别等条件做 AND/OR 组合过滤。
- 怎么做的：Spring Boot 动态 SQL 构造 WHERE + 复合索引（2 万行量级无需 ES）→ 前端筛选表单 → JSON 查询条件 → 分页返回。
- 可能遇到的问题：
1. 应届身份有语义模糊地带（择业期两年内未就业算不算应届）——产品层必须用表单强制二选一，数据库只做等价转换
2. 枚举字段索引设计需按高频组合调优
- 结论：零技术风险，标准 CRUD+索引工程，正确性（与 Excel 手工筛选 100% 一致）与性能（P95<200ms）均可量化验收。

技术点 4竞争比/进面分的高精度预测

- 处理的问题：预测某岗位最终报名人数、竞争比、进面分数线。
- 怎么做的：历史进面分 + 报名增量 + 岗位特征做回归/时序模型 → 输出预测值。
- 可能遇到的问题：
1. 样本极稀疏（每岗位每年只有 1 个最终值，年份间分布漂移大）
2. 不可观测变量（弃考率、改报行为、跟风心理无法建模）
3. 验证关（回测结果不能代表当年，前向验证只能在次年事后对账）
- 结论：高精度预测不可实现（数据结构决定）；可降级为"参考区间 + 实时展示"（第 4~6 天当日竞争比本身是强信号），产品承诺务必降级。

技术点 5招录政策的年度变动预测

- 处理的问题：预判明年招录规模、专业范围、应届政策的调整。
- 怎么做的：对历史政策数据建模 → 预测下一年政策。
- 可能遇到的问题：
1. 政策由行政决策驱动，无公开可建模的确定规律，历史上规模/年龄/倾斜比例均出现无规律调整
2. 验证关——无法对"未发生的事件"建立可验证模型
- 结论：预测不可实现；应对是架构配置化（招考规则做成年度配置项，公告发布后 1 周内完成切换），把"年度适配流程"当工程能力建设。

技术点 6官方限制瓶颈（无 API / 实时数据延迟 / 反爬红线）

- 处理的问题：① 官方提供 API 直接取数；② 竞争比分钟级实时；③ 高效抓取官方报名系统。
- 怎么做的：公告期窗口采集官方公开数据 + 每日同步节奏 + 合规采集三原则（只抓公开页、守 robots 控频、注明来源）。
- 可能遇到的问题：
1. 治理关（官方不提供公开 API 且无开放计划
2. 官方报名人数每日只更新一次 → 产品天然存在"一日延迟"，任何技术无法突破）
3. 法律关（突破反爬可能触犯非法获取计算机信息系统数据罪
4. 公务员及报考人员个人信息受法律严格保护，采集即违法——能做≠能上）
- 结论：数据获取受治理+法律双重约束，技术上不可绕过；合规采集已覆盖产品 90% 数据需求（职位表/专业目录/每日过审人数均为官方公开），产品设计围绕"每日更新"节奏，并作为立项红线写死。

技术点 1RAG 问答（职位/真题/资讯）

- 处理的问题：用户自然语言提问（"北京应届计算机硕士，有哪些竞争小一点的岗？"），系统检索 + 生成带依据的回答。
- 怎么做的：职位/真题/资讯向量化入 pgvector（HNSW）→ 混合召回（向量 + BM25，权重可配）→ DeepSeek 生成（系统提示词"只允许基于检索结果回答"）→ 输出结构化 JSON（岗位列表+理由链+引用来源）。
- 可能遇到的问题：
1. 向量检索对结构化短文本职位未必优于规则精确匹配——正确姿势是"规则过滤为主、向量召回应答为辅"
2. 幻觉只能压到极低不能归零（见 AI 能力层技术点 2）
3. 评测集标注有偏差，需双人标注一致性（Kappa≥0.8）
4. 0.008 元/次是估算，必须实测修正
- 结论：技术可行，但"评测体系 + 引用约束"是投入重点（幻觉率≤3%、引用可核验≥95% 为硬验收指标）。

技术点 2AI 幻觉的 100% 消除

- 处理的问题：让 LLM 永不输出编造的岗位、条件、政策。
- 怎么做的：RAG 检索约束 + 输出引用强制标注 + Judge LLM 二次校验 + 人工复核通道 + 免责声明。
- 可能遇到的问题：
1. 原理关（LLM 本质是概率式 token 生成，不存在"确定性保证"机制，幻觉率只能压到 1~5%，理论无法归零）
2. 验证关（评测集只能证明"测试集上幻觉率≤X%"，无法证明"所有输入都不幻觉"）
- 结论："归零"不可实现，"受控"可实现——以"幻觉率≤3%（评测集）+ 引用可核验"为可验收标准，配套免责与人工兜底。

2.1.4 资讯系统

  • 内容聚合管线（RSS + 爬虫）+ 分类 + AI 摘要 + 搜索
  • 难度：★☆☆

技术点 1资讯聚合 + AI 摘要

- 处理的问题：聚合时政/官方公告/面试技巧，分类 + 摘要 + 搜索。
- 怎么做的：RSS + 白名单爬虫（遵守 robots）→ simhash 去重 → LLM 分类（few-shot）→ LLM 摘要（≤150 字+关键词）→ PG 全文索引（一期）→ 列表 + Tab + 热门排行（Redis 计数）。
- 可能遇到的问题：
1. 版权是真实风险（转载需注明来源、控制摘录篇幅，整篇搬运有侵权风险）
2. 大站 WAF 需控频（≤日均 1/3）+ UA 合规 + 失败退避，不做绕过
- 结论：技术成熟（分类≥90%、采集成功率≥95% 可验证），风险集中在版权与反爬合规边界，属产品策略问题。

4. 技术侧初步评估结论

4.1 总体判断

产品思路在技术层面只有有限范围可行：真正具备成熟实现条件的功能，仅限于基础选岗匹配、RAG 问答、公开资讯展示三项；其余涉及核心竞争价值的功能（题库内容、竞争比预测、AI 权威评分、实时数据等）均存在重大技术或数据障碍，短期难以达到可用水平，整体方案按预期推进的可能性较低。

4.2 可行部分（实现条件成熟）

以下功能有成熟技术方案，可在 3-4 人、2-3 个月左右完成基础版本：

功能 实现条件 说明
基础选岗匹配 官方职位表（Excel）+ 专业目录为公开数据，规则匹配成熟 仅限静态条件筛选（专业/学历/政治面貌等），不包含竞争比动态数据
RAG 问答 职位数据向量化 + 大模型 API，单次成本约 0.008 元（估算） 可回答选岗相关问题，但受幻觉边界约束，只能"参考建议"
公开资讯展示 RSS + 爬虫聚合，技术成熟 时政/公告/面试技巧展示，需注意版权边界

需清醒认识：以上可行功能均为"公开信息工具"层面的能力，技术门槛不高，与市场上现有免费工具（粉笔筛选器、公考雷达等）难以形成差异化。

4.3 不可行或高度受限部分（主要障碍）

功能/能力 障碍性质 具体问题
题库内容建设 重资产 10 万+ 真题结构化 + 解析 ≈ 4-12 人年；公开合法题源极少（版权壁垒）
竞争比/进面分预测 数据受限 官方每年仅 10 天窗口、每岗位每年 1 个观测值，跨年不可比，高精度预测不可实现
实时竞争比 治理受限 官方无 API、每日仅更新一次，产品天然存在"一日延迟"，无法突破
AI 权威评分 原理受限 主观题无权威评分基准，LLM 相关性仅 0.6-0.8，不能承担"权威评分"责任
AI 幻觉消除 原理受限 大模型概率生成本质，幻觉只能压到 ≤3%，无法归零
真实报名数据 法律红线 公务员及报考人员个人信息受法律严格保护，"能做≠能上"
招录政策预测 不可建模 政策由行政决策驱动，无规律可循

4.4 团队与投入评估

  • 现有能力（Web 建站、系统集成、数据库部署）可复用，但 LLM/AI 工程、数据采集、题库标注均为新建能力，存在明显缺口。
  • AI 相关部分需外聘或外包，增加 0.5-1 人成本；数据运营为持续性投入。
  • 合规成本：生成式 AI 服务需登记（前置数周），爬虫需严格守合规红线。

4.5 总体评价

综合评估，本方案存在以下突出问题：

  1. 可行部分缺乏差异化：基础选岗匹配、RAG 问答、资讯展示均与市场现有免费工具高度重合，难以形成产品竞争力。
  2. 核心价值功能短期无法实现：题库内容、竞争比预测、AI 权威评分等差异化能力，均受重资产、数据或原理层面的硬约束，短期内无法达到预期。
  3. 技术难度被低估：AI 工程、数据采集、题库标注等能力需从零建设，涉及大量人力与时间投入，且部分功能（预测、评分）受原理约束，投入也不一定能达到预期效果。
  4. 合规与数据红线：多个理想功能受法律与数据源约束，产品定位只能局限为"公开信息工具"。
